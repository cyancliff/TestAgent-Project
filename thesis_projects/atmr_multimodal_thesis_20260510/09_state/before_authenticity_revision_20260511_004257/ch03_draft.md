# 第3章 系统需求分析与总体设计
<!-- chapter_id: ch_3 -->

## 3.1 需求分析

本文系统面向普通用户和毕设演示场景，核心需求是完成一次从测评到解释再到咨询的完整闭环。用户侧需要注册登录、上传头像、开始测评、恢复进度、完成阶段作答、查看历史报告、上传视频生成大五人格报告，并在对话中关联已有报告继续提问。管理和工程侧则需要保证接口结构清晰、任务状态可追踪、报告结果可持久化、关键流程可测试。

系统的功能需求可以分为六类。第一类是用户与认证需求，包括注册、登录、当前用户信息和头像上传。第二类是 ATMR 测评需求，包括草稿创建、阶段答题、题目恢复、阶段提交、报告生成、历史查询和会话删除。第三类是智能分析需求，包括自适应选题、异常作答检测、多智能体辩论和 RAG 证据检索。第四类是大五人格视频报告需求，包括视频上传、任务创建、后台推理、结果查询、报告保存和 AI 解读。第五类是聊天咨询需求，包括会话创建、历史消息、报告关联和上下文读取。第六类是部署与运维需求，包括健康检查、静态文件挂载、Docker 部署和数据库迁移。

非功能需求主要包括可靠性、可解释性、可扩展性和边界控制。可靠性要求系统在用户中断、后台任务失败、多模态依赖缺失时能够给出明确状态，而不是无声失败。可解释性要求报告有证据来源，异常作答和模型版本能够被记录。可扩展性要求 ATMR主线与大五人格辅线保持低耦合，后续可以接入新的模型或新的知识库。边界控制要求系统不把自动分析结果写成医学诊断，不把尚未完成的实验写成既定事实。

## 3.2 总体架构设计

系统总体采用前后端分离结构。前端基于 Vue 3，负责页面交互、状态展示和用户操作入口；后端基于 FastAPI，负责业务接口、认证、测评流程、报告生成、多模态任务和知识检索；数据库负责用户、测评会话、答题记录、报告和聊天记录等数据持久化；离线多模态目录负责预处理、训练、评估和 checkpoint 产出。

[[FIG:系统总体架构图]]

从证据链角度看，系统包含 ATMR 问卷主线和视频多模态辅线。ATMR 主线从用户作答中得到四阶段测评结果，并通过多智能体辩论和 RAG 生成综合报告；视频多模态辅线从上传视频中得到 Big Five 五维分数，并生成独立大五人格报告。两条证据链在历史页和聊天页并列呈现，既能让用户分别查看，也能在咨询场景中被同时读取。

从工程边界看，系统将在线服务和离线训练分离。在线服务只负责接收请求、调用已验证 checkpoint、保存任务状态和展示结果；离线训练则负责耗时的特征提取、全量训练、评估指标汇总和模型调参。这样做可以减少训练依赖对在线系统的影响，也使论文中能够清楚地区分“系统功能实现”和“模型实验过程”。

后端路由按业务域划分：assessment 负责测评流程，auth 负责认证，chat 负责咨询对话，rag 负责知识库检索，multimodal-personality 负责大五人格视频任务。服务层进一步封装 StageService、QuestionSelectionService、MultimodalPersonalityService 等核心逻辑，避免路由函数直接承担复杂业务。

## 3.3 ATMR 测评主流程设计

ATMR 测评主流程以会话为中心。用户进入测评页后，系统先检查是否存在未完成会话；若存在，则提示继续测评或修改答案；若不存在，则创建新的测评草稿。用户在每个阶段完成题目后，系统保存答题记录，并根据阶段状态决定是否进入模块评审或最终报告。

[[FIG:ATMR测评主流程图]]

题目展示与阶段提交需要兼顾灵活性和约束性。前端提供题目列表、当前题、上一题、下一题、补充说明和阶段提交按钮；后端则负责校验会话归属、保存答案、记录时间、识别异常和更新 submitted_stages。为了避免空会话污染数据库，系统在开始阶段采用草稿策略，只有当用户进入实际作答后才持久化有效会话。

报告生成流程强调异步状态和可恢复体验。当用户完成所有阶段后，系统进入报告整理状态，并把测评记录保留下来。若报告生成暂时未完成，用户仍可到历史记录查看后续结果。这样的设计符合在线应用的真实使用需求，避免用户必须停留在当前页面等待所有大模型调用结束。

## 3.4 多模态人格预测子系统设计

多模态子系统采用独立复现层和在线接入层两级结构。独立复现层位于 multimodal_personality 目录，负责数据配置、预处理、特征提取、模型定义、训练、评估和推理；在线接入层位于 app/api 和 app/services 中，负责视频上传、任务创建、checkpoint 加载、报告状态同步和结果持久化。

[[FIG:多模态人格预测流程图]]

离线链路从 CFI-V2 manifest 构建开始。系统根据数据集标注和转写文件生成 train、val、test 三个阶段的样本清单，然后执行视频抽帧、音频提取和 Whisper 转写。之后，CLIP 提取视觉帧和文本句子的特征，wav2clip 提取音频片段特征，bg_features用于补充工程版背景关联特征。最终，feature bundle 将四路输入组织为统一 JSON，以供训练、评估和在线推理复用。

在线链路以任务记录为中心。用户上传视频后，服务层为文件生成 task_id，并将任务状态写入本地 JSON 或数据库报告记录。后台任务执行时先进行预处理和特征提取，再加载当前默认 checkpoint 生成 Big Five 分数。若依赖缺失或 checkpoint 不存在，系统会保留错误信息并使用明确的失败或回退状态，而不是返回看似真实的结果。

大五人格报告独立于 ATMR 报告。报告表中记录 task_id、用户、来源测评、原始文件名、模型版本、五维分数、工件路径、错误信息、是否真实模型结果和 AI 解读状态。只有真实完成且模型版本匹配的结果，才会进入 AI 解读流程；占位结果或失败结果不会被写成正式分析。

## 3.5 数据库与文件组织设计

系统数据既包含关系型数据，也包含文件型工件。关系型数据包括用户信息、测评会话、答题记录、模块辩论结果、聊天会话、大五人格报告等；文件型工件包括头像、上传视频、多模态中间文件、报告解释文件、模型 checkpoint 和实验日志。二者通过数据库字段中的路径或任务编号建立关联。

ATMR 主线的数据结构以 AssessmentSession 和 AnswerRecord 为核心。AssessmentSession 保存用户、状态、当前阶段、提交阶段、报告路径和修订信息；AnswerRecord 保存题号、选项、得分、作答时间、异常标记和补充说明。这样的结构支持恢复、重新开始、复制会话和删除相关依赖记录。

多模态部分的数据结构以 BigFivePersonalityReport 和任务工件为核心。视频文件保存在 uploads/multimodal_personality下，任务 JSON 记录保存在 tasks 目录，中间特征和预处理结果保存在 artifacts 目录。该设计虽然比完全数据库化更轻量，但便于离线调试和论文复现；后续若系统规模扩大，可将后台任务迁移到正式任务队列，并将工件索引进一步规范化。

## 3.6 安全性与可靠性设计

系统在用户数据访问上采用所有权校验。测评会话、历史报告和大五人格报告都需要校验当前用户是否拥有对应资源，避免用户通过猜测 ID 访问他人数据。上传文件也需要检查文件名和内容是否为空，并将实际保存文件名改写为随机标识，减少路径冲突。

在可靠性方面，系统为多模态模块设计了依赖检测和失败回退。主应用加载多模态路由时采用异常捕获，避免多模态依赖问题导致整个后端无法启动。多模态服务运行时检查 torch、checkpoint、CLIP、wav2clip 等依赖状态，并在失败时记录错误列表。

在解释安全方面，系统将报告定位为辅助分析，不提供临床诊断。ATMR 报告和 Big Five 报告都应强调使用边界，尤其是大五视频预测结果容易受到视频场景、光照、音频质量、说话内容和模型训练数据分布影响，不能作为单独判断个体人格或心理健康状态的依据。

## 3.7 前端交互与用户体验设计

前端交互设计直接影响测评系统能否被完整使用。心理测评流程通常比普通表单更长，如果界面只提供题目和选项，用户很容易在阶段切换、返回修改、报告等待和历史查看过程中迷失。因此，本文前端将测评页设计为具有开始页、答题页、阶段评审页和结果页的多状态界面，并在不同状态下展示不同操作入口。

在开始页中，系统先检查用户是否存在未完成会话。若存在，页面突出显示“继续测评”和“修改答案”入口，避免用户误以为必须重新开始；若用户已完成过测评，页面提供“开始新测评”和“查看历史报告”入口。这样的设计把会话状态前置给用户，减少因状态不透明造成的重复作答。

在答题页中，前端同时展示阶段进度和总进度。阶段进度帮助用户理解当前模块完成情况，总进度帮助用户估计整体剩余时间。题目导航采用可展开列表，使用户可以查看已答和当前题号，但仍通过后端阶段规则约束最终提交。补充说明按钮始终可见，尤其当某题触发异常追问时，用户可以及时补充原因，避免报告解释完全依赖系统推断。

在报告生成阶段，前端使用加载状态提示“专家评审中”和“正在整理最终报告”。这些提示并不是装饰性文本，而是对后台异步任务的用户侧反馈。由于多智能体辩论、RAG 检索和报告整理可能需要一定时间，如果界面没有明确状态，用户容易误判系统卡死。通过阶段化提示和历史页兜底，系统可以让用户在等待过程中保持可控感。

大五人格报告页则采用信息分区结构。顶部展示报告标题、创建时间和状态；主体区域展示雷达图和五维分数条；来源区域展示视频文件、模型版本和结果性质；解读区域展示 AI 生成的结构化说明；底部提供返回历史、重新生成和用于对话等操作。这种分区方式使用户能够先看整体画像，再查看具体维度和解释边界。

聊天页的交互设计强调上下文选择。用户可以在同一会话中选择是否关联 ATMR 报告和大五人格报告，系统不会自动把所有报告混入对话。这样既能减少无关上下文对回答的干扰，也让用户清楚知道当前咨询依据了哪些材料。对于心理测评系统而言，上下文透明比单纯追求智能化更重要。
