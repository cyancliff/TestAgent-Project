## 3. 主要发现

下面按严重程度排序。

### 3.1 [高] 多模态接口当前是未鉴权公开的，而且允许客户端登记任意服务器本地路径

相关位置：

- `app/main.py:55-60`
- `app/api/multimodal_personality.py:38-80`
- `app/schemas/multimodal_personality.py:12-17`
- `app/api/multimodal_personality.py:16-29`

问题描述：

- 主应用直接挂载了多模态路由。
- 路由里没有 `Depends(get_current_user)`，也没有任何 router 级别的权限控制。
- `POST /upload` 允许客户端直接提交 `video_path`。
- 返回结构会把 `video_path`、`artifacts` 等内部路径直接回传给调用方。

我实际验证到的行为：

- 未登录访问 `GET /api/v1/multimodal-personality/health` 返回 `200`。
- 未登录访问 `POST /api/v1/multimodal-personality/upload` 也返回 `200`。
- 传入 `C:\Windows\not-real-demo.mp4` 这样的本地路径也会被成功登记为任务。

风险：

- 任何能访问接口的人都可以创建多模态任务。
- 外部请求可以把服务端本地路径塞进任务里，后续再交给 `ffmpeg/whisper` 流程处理。
- 接口响应会暴露服务器内部文件路径和工件目录结构。

建议：

1. 至少给 `upload`、`upload-file`、`run`、`result` 加上登录鉴权。
2. 禁止客户端直接提交任意本地路径，改成只允许“系统已保存的上传文件”或“白名单目录”。
3. 对外响应不要再返回绝对路径，改成任务状态、下载 token 或受控资源 ID。

### 3.2 [高] 多模态执行现在会阻塞请求线程，而且全局锁把其它任务查询也串行卡住了

相关位置：

- `app/api/multimodal_personality.py:64-71`
- `app/services/multimodal_personality_service.py:171-203`
- `multimodal_personality/inference/pipeline.py:132-212`

问题描述：

- `run` 是 `async def`，但内部直接同步调用 `service.run_task(...)`。
- `run_task()` 在 `with self._lock:` 里执行了整个 pipeline。
- pipeline 内部包含 `subprocess.run(ffmpeg)` 和 `whisper.load_model()/transcribe()` 这类长耗时操作。

我实际验证到的行为：

- 把 pipeline 人为放慢到 `2s` 后，另一个本应很轻的 `get_task()` 调用也被一起阻塞了约 `2.01s`。

风险：

- 一个长视频任务就可能把多模态接口整体拖慢。
- 状态轮询、结果查询、其它新任务创建都会被同一把锁卡住。
- 如果线上 worker 数不高，用户体感会非常差。

建议：

1. 把真正的执行搬到后台任务队列或独立 worker。
2. 缩小锁粒度，只在读写 `_tasks` 字典和落盘时加锁，不要把整段推理流程包进锁里。
3. `run` 接口更适合改成“提交任务后立即返回”，再用轮询或回调拿结果。

### 3.3 [中高] 视频上传会一次性把整个文件读进内存，而且没有大小/类型保护

相关位置：

- `app/api/multimodal_personality.py:49-60`
- `app/services/multimodal_personality_service.py:108-123`

问题描述：

- `upload-file` 里直接 `content = await file.read()`，这会把整个视频一次性读入内存。
- 后面又把 `content` 整块写盘。
- 当前没有看到文件大小上限、MIME 类型检查、扩展名白名单或上传配额控制。

风险：

- 大文件上传时容易出现高内存占用。
- 在未鉴权前提下，这会进一步放大 DoS 风险。
- 非视频文件也可能被当作“视频任务”进入后续流程，直到 ffmpeg 阶段才失败。

建议：

1. 改成分块流式写盘。
2. 加文件大小限制。
3. 增加内容类型/扩展名校验，必要时补充病毒扫描或最少的魔数校验。

## 5. 你的多模态视觉系统现在可以干什么

基于当前代码，不看外部目标，只看仓库里的真实实现，你的多模态系统现在已经能做这些事：

### 5.1 在线接口能力

通过 FastAPI 提供：

- `POST /api/v1/multimodal-personality/upload`
  - 登记一个本地视频路径，生成任务。
- `POST /api/v1/multimodal-personality/upload-file`
  - 接收上传文件，保存到 `uploads/multimodal_personality/videos/`，再生成任务。
- `POST /api/v1/multimodal-personality/run`
  - 触发一次多模态预处理/占位推理流程。
- `GET /api/v1/multimodal-personality/result/{task_id}`
  - 查询任务状态、错误和工件。
- `GET /api/v1/multimodal-personality/health`
  - 检查系统工具和模块可用性。

### 5.2 当前已经打通的预处理链路

在 `multimodal_personality/inference/pipeline.py` 里，当前已经能完成：

1. 检查系统是否有 `ffmpeg`、`ffprobe`、`whisper`。
2. 对视频均匀抽帧，输出最多 `15` 张 `336x336` 图片。
3. 从视频中抽取单声道 `16kHz` 音频。
4. 用本地 Whisper 模型做转写，写出 `transcript.txt`。
5. 生成 `manifest.json` 记录执行阶段、成功状态和错误信息。

另外，今天我实际调用健康检查时，接口返回：

- `ffmpeg = true`
- `ffprobe = true`
- `whisper = true`

这说明你当前这台机器已经具备跑“视频预处理 + 音频提取 + 本地转写”的基础环境。

### 5.3 离线数据工程能力

当前仓库还已经具备一套离线数据处理脚手架：

- `scripts/build_cfi_v2_manifest.py`
  - 从 `annotation.pkl` 和 `transcription.pkl` 生成标准化 `train/val/test manifest`。
- `scripts/preprocess_cfi_v2_from_manifest.py`
  - 批量读取 manifest，对视频样本跑预处理。
- `scripts/build_clip_feature_jobs.py`
  - 根据 manifest 和预处理工件生成 CLIP 特征任务。
- `scripts/extract_clip_features.py`
  - 读取预处理帧和文本，输出 CLIP 图像/文本特征 JSON。

### 5.4 特征层面现在已经能做的事

在 `multimodal_personality/feature_extractors/clip_extractor.py` 里，已经支持：

- 用 `openai/clip-vit-large-patch14-336` 提取抽帧后的图像特征。
- 用同一套 CLIP 文本编码器提取转写文本特征。
- 把每个样本输出成 JSON，包含：
  - 图像特征维度
  - 文本特征维度
  - 图像特征向量
  - 文本特征向量

这意味着你现在已经不是“只能上传视频”，而是已经能把视频转换成后续模型可用的视觉/文本表示。

## 9. 除多模态之外新增发现

这一轮补充 review 主要看了认证、RAG、聊天会话和评测报告链路。

### 9.1 [高] 注册接口允许空密码直接注册成功

相关位置：

- `app/api/auth.py:29-31`
- `app/api/auth.py:47-72`

问题描述：

- `AuthRequest` 只有 `username` 和 `password` 两个裸字符串字段，没有 `min_length`、复杂度或非空约束。
- `register()` 里只校验了 `username.strip()`，没有对密码做任何校验。

我实际验证到的行为：

```powershell
POST /api/v1/auth/register
{"username": "u57889f47", "password": ""}
```

返回：

- `200`
- 成功创建账号并签发 token

风险：

- 空密码账号会直接进入系统。
- 后续所有基于“已注册即有基本口令强度”的假设都不成立。

建议：

1. 给 `password` 增加最小长度约束，至少 `min_length=8`。
2. 最好补充服务端复杂度校验，而不是只靠前端。
3. 为注册/登录补上密码边界测试。

### 9.2 [高] RAG 接口全部公开，无鉴权也能直接调用和消耗后端能力

相关位置：

- `app/api/rag.py:35-105`

问题描述：

- `/rag/query`
- `/rag/retrieve`
- `/rag/structure`
- `/rag/status`

这四个端点都没有 `Depends(get_current_user)`，也没有限流。

我实际验证到的行为：

- 未携带任何 token 时，上述 4 个接口全部返回 `200`。
- `/rag/query` 和 `/rag/retrieve` 可以直接触发知识库检索。
- `/rag/status` 会公开返回 `doc_id` 和文档元数据。

风险：

- 外部请求可以直接消耗 RAG 相关算力和第三方 API 成本。
- 知识库结构和文档元数据会被公开暴露。

建议：

1. 至少要求登录后才能访问。
2. 给这些接口加限流。
3. 如果只是内部调试用途，建议彻底下线 `structure/status` 对公网的暴露。

### 9.3 [中高] 聊天会话切换评测后，只重建 system prompt，不清空旧对话，导致上下文串线

相关位置：

- `app/api/chat.py:237-259`
- `app/api/chat.py:477-520`

问题描述：

- `update_chat_session()` 允许把一个聊天会话重新关联到另一份评测。
- 关联变化后会调用 `init_chat_with_context()`。
- 但 `init_chat_with_context()` 只删除旧的 `system` 消息，不删除旧的 `user/assistant` 消息。

我实际验证到的行为：

- 原本属于评测 `8` 的用户消息 `old-msg` 仍然保留。
- 重新初始化后，新的 `system` 消息已经切换到评测 `9`。
- 最终同一个聊天会话里出现了“旧对话 + 新评测系统提示”的混合上下文。

验证输出片段：

```text
[('user', 'old-msg', 8), ('system', '你是一位专业的心理咨询师和心理分析专家。', 9)]
```

风险：

- 切换评测后继续聊天时，模型会同时看到旧评测对话和新评测上下文。
- 这会直接污染建议内容，属于行为级错误，不只是体验问题。

建议：

1. 如果允许重新关联评测，应清空历史 user/assistant 消息。
2. 或者更稳妥：禁止把已有消息的会话重新绑定到另一份评测，改成新建会话。

### 9.4 [中] `finish-stream` 走 query token 鉴权，而且当前前端并未使用这条路径

相关位置：

- `app/api/assessment/streaming.py:397-409`
- `README.md` 中的 API 描述

问题描述：

- 这个接口不走标准 `Bearer` 依赖，而是手动接收 `token` query 参数。
- query token 容易出现在浏览器历史、代理日志和访问日志里。
- 我搜索了 `frontend/src`，没有找到对 `finish-stream` 的实际调用，前端当前用的是提交后轮询报告。

风险：

- 保留了第二套不一致的鉴权方式。
- 还增加了 token 泄露面。
- 由于它也会触发综合辩论/报告生成，后续容易和现有后台报告流程产生重复逻辑。

建议：

1. 如果不再使用，建议删除。
2. 如果要保留，改成标准登录依赖，不要再收 query token。
